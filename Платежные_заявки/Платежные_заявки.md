# Регламент управления процессом платежей и платёжным календарём в системе Битрикс24

## 1. Общие положения

- **Цель документа:** Оптимизация движения денежных средств, оперативное выявление и предотвращение кассовых разрывов, автоматизация контроля расходов.
- **Область применения:** Регламент обязателен для всех сотрудников и подразделений компании, инициирующих, согласующих или исполняющих выплаты.
- **Главный принцип:** Ни один платёж не может быть осуществлён без фиксации заявки в Битрикс24, прохождения настроенного маршрута согласования и включения в матричный платёжный календарь.

---

## 2. Матрица зон ответственности и приоритетов

Процесс обработки заявки, требуемый пакет документов и уровень приоритета жестко зависят от экономической природы платежа:

| **Налоги и сборы** | Главный бухгалтер / бухгалтер | Налоговая декларация, требование ИФНС, расчетная справка | **1 — Критический** | Сверхприоритет. Сроки жестко регламентированы законодательством. |

## 3. Архитектура заявки в Битрикс24 (обязательные поля)

Процесс реализуется в Битрикс24 через модуль **«Смарт-процессы»**. Каждая заявка должна содержать заполненными следующие поля:

1. **Название заявки:** Автоматическая маска `[Зона ответственности] Наименование контрагента`.
2. **Зона ответственности:** Выпадающий список (*Кредиты/Займы, Налоги, ЗП, Поставщики, Расходы по реализации, Иное*).
3. **Сумма и валюта:** Числовое поле (по умолчанию BYN).
4. **Основание платежа:** Текстовое поле по маске:  
   `[Тип документа] №[Номер] от [Дата], [Краткое назначение платежа], Ставка НДС (0%-25% или Без НДС)`.
5. **Крайний срок оплаты:** Предельная дата оплаты по договору или закону.
6. **Планируемая дата платежа:** Дата, в которую платёж будет фактически отправлен (устанавливается Казначеем).
7. **Приоритет:** Выпадающий список (*1-Критический, 2-Высокий, 3-Средний, 4-Низкий*).
8. **Скан-копия документа:** Поле типа «Файл» для загрузки счёта/требования/ведомости (необязательно к заполнению).
9. **Получатель (Контрагент):** Официальное наименование контрагента (выбор из справочника САП).

# Техническое описание и регламент бизнес-процесса

**«Управление платёжными заявками и матричным Платёжным календарём в Битрикс24 с последующей интеграцией в SAP»**

---

## 4. Этапы движения заявки (Канбан-воронка)

Заявка последовательно проходит следующие автоматизированные стадии в Битрикс24:

`[Черновик]` → `[Согласование руководителем подразделения]` → `[Контроль Казначейства]` → `[Утверждение Реестра]` → `[В работе (Бухгалтерия)]` → `[Оплачено]`

**Дополнительная цикличная стадия (вне основного потока):** `[На доработке (Инициатор)]`

---

## 5. Подробное описание этапов и автоматических маршрутов

### Стадия 1. Черновик
- Инициатор заполняет карточку и прикрепляет файлы. Заявка видна только автору.
- **Прямой маршрут (Автоматическое списание / Ускоренная фиксация):**
  - Возможность выбора типа операции *«Прямое списание (без согласования)»* (для пеней госорганов, инкассо, комиссий банка, списаний по платёжным требованиям и т.д.) технически доступна исключительно **Казначею, Главному бухгалтеру и Бухгалтеру**.
  - При создании такой заявки уполномоченным сотрудником и прикреплении подтверждающего документа робот автоматически пропускает стадии 2, 3 и 4, мгновенно направляя карточку на стадию `[В работе (Бухгалтерия)]` для последующей передачи в SAP.
  - Для рядовых сотрудников данный тип заявки скрыт.

### Стадия 2. Согласование руководителем
- Робот отправляет задание руководителю отдела.
- **Исключение (Защищённые статьи):** Если выбрана зона *«Налоги и сборы»* или *«Заработная плата»*, робот автоматически пропускает этот этап и отправляет заявку сразу на этап контроля.
- **Маршрут возврата:** Если руководитель отклоняет заявку из-за ошибки, он обязан указать причину в комментариях. Робот автоматически переводит карточку на стадию `[На доработке (Инициатор)]`.

### Стадия 3. Контроль Казначейства (Финансовый отдел)
- Казначей проверяет корректность реквизитов, лимиты бюджетов и выставляет *«Планируемую дату платежа»*, автоматически включая заявку в Платёжный календарь.
- **Маршрут возврата (Уточнение заявки):** Если казначей находит ошибку, он вносит замечание в карточку и переводит её на стадию `[На доработке (Инициатор)]`. Заявка при этом автоматически временно исключается из Платёжного календаря.
- **Частичное удовлетворение (Разделение заявки):** Если казначей согласовывает оплату заявки не в полном объёме, он активирует признак частичной оплаты и указывает сумму к уменьшению. Робот автоматически делит исходную заявку на две:
  1. **Первая (одобренная часть):** остаётся в текущей карточке со сниженной суммой и движется далее на этап `[Утверждение Реестра]`.
  2. **Вторая (остаток):** автоматически копируется роботом в новую связанную карточку и возвращается на доработку/согласование казначею на текущую стадию `[Контроль Казначейства]`.

### Изолированная стадия. На доработке (Инициатор)
- Сюда заявка попадает со стадий 2 или 3.
- На этой стадии для Инициатора вновь открывается доступ на редактирование полей *«Сумма»* и *«Получатель»*.
- После исправления данных Инициатор нажимает кнопку **«Исправлено»**, и робот отправляет заявку обратно на ту стадию, с которой она была возвращена.
- **Регламентный дедлайн:** На исправление заявки Инициатору отводится ровно **1 рабочий день (24 часа без учёта выходных)**. Если за 1 день Инициатор не внёс правки, робот автоматически переводит карточку в статус *«Отклонено/Аннулировано»* и уведомляет автора.

### Стадия 4. Утверждение Реестра
- Директор/уполномоченное лицо ежедневно **до 14:30** утверждает пул заявок на текущий/следующий день.
- Изменение данных после этой стадии технически блокируется системой. Возврат на доработку отсюда невозможен.

### Стадия 5. В работе (Бухгалтерия)
- Заявка падает в бэклог бухгалтера-операциониста для последующего исполнения в Банк-Клиент.
- Сюда поступают как стандартные/частично одобренные платежи, так и заявки прямого маршрута от бухгалтерии/казначейства.
- **Битрикс24 выступает в роли мастер-системы.**

### Стадия 6. Оплачено
- Финальная стадия. После проведения платежа банк-клиентом и подтверждения списания по выписке, бухгалтер вручную переводит карточку в этот статус.
- **Интеграционный триггер (Выгрузка в SAP):** Переход в статус *«Оплачено»* инициирует автоматическую выгрузку параметров платежа из Битрикс24 в SAP для автоматического формирования бухгалтерского документа списания по банковским счетам.

## 6. Формирование и ведение матричного Платёжного календаря

Матричный Платёжный календарь формируется **автоматически** на основании данных из утверждённых и находящихся на контроле платёжных заявок в Битрикс24 в виде интерактивной сетки по дням и неделям.

### 6.1. Автоматическое распределение сумм

- **Стандартные заявки:** Попадают в календарь после заполнения казначеем поля *«Планируемая дата платежа»* на стадии 3. Если заявка отправляется на стадию `[На доработке]`, она мгновенно исчезает из сетки календаря до момента повторного согласования.
- **Заявки прямого маршрута:** Отображаются в календаре мгновенно в день их создания.
- **Синхронизация при разделении:** При частичном удовлетворении одобренная часть остаётся на исходную дату, а созданный остаток (дочерняя заявка) временно скрывается из сетки дат и отображается заново только после назначения казначеем новой плановой даты.

### 6.2. Матрица приоритетов и зон ответственности (Визуальное разделение)

*В документе подразумевается цветовое или структурное разделение заявок в календаре по зонам ответственности и приоритетам (настройка визуализации в Битрикс24).*

## 7. Права доступа и контроль полей

### 7.1. Поле «Сумма заявки» (Тип: Число)

- **Стадия «Черновик» и «На доработке»:** Открыто и обязательно для заполнения Инициатором.
- **Стадии от «Согласование руководителем» до «В работе»:** Поле заблокировано для редактирования для Инициаторов и Руководителей (доступно только Казначею и Гл. бухгалтеру).

### 7.2. Поле «Получатель / Контрагент» (Тип: Привязка к CRM)

- **Стадия «Черновик» и «На доработке»:** Открыто и обязательно для заполнения Инициатором.
- **Права просмотра:** Обычные сотрудники видят получателей только в рамках своего отдела. Казначей, Директор и Бухгалтерия имеют сквозной доступ ко всем контрагентам.
- Со стадии `[Утверждение Реестра]` поле блокируется для всех.

---

## 8. График платежного дня (Тайминги)

Процесс обработки и исполнения платежей жестко регламентирован по времени. Нарушение таймингов автоматизировано системой:

- **До 10:30** — Создание заявок инициаторами и их согласование руководителями отделов в Битрикс24.
- **С 11:00 до 13:00** — Анализ Казначеем матричного платёжного календаря, проверка лимитов, балансировка кассовых разрывов и утверждение дат выплат (перевод проверенных заявок на стадию `[Утверждение Реестра]`).
- **С 13:00 до 14:00** — Проверка и финальный акцепт сформированного реестра Генеральным или Финансовым директором.
- **С 14:00 до 15:00** — Формирование и выгрузка платежей бухгалтером в Банк-Клиент, отправка денежных средств.
- **С 16:30 до 17:30** — Проверка выписок, перевод заявок бухгалтером на финальную стадию `[Оплачено]` и автоматическая отправка данных в SAP для формирования документов списания по счетам.

> **Правило жесткой отсечки:** Заявки, не успевшие пройти согласование руководителя подразделения **до 11:00** текущего дня, автоматически переносятся роботом Битрикс24 на следующий платёжный день (планируемая дата сдвигается на +1 день).

---

## 9. Контроль и ответственность

- **Финансовая дисциплина:** Попытки проведения оплат в обход настроенного смарт-процесса Битрикс24 признаются грубым нарушением финансовой дисциплины и влекут за собой административную ответственность.
- **Обязательность аргументации:** В случае отклонения заявки или её возврата на доработку на любом из этапов, согласующее лицо (Руководитель, Казначей, Директор, бухгалтер) обязано оставить **текстовый комментарий** в карточке Битрикс24 с указанием точной причины отказа. Без заполнения этого комментария система технически блокирует смену статуса. Инициатор мгновенно получает автоматическое уведомление и задачу на доработку со сроком в 1 день.

## Инструкция по настройке прав доступа к смарт-процессу «Платежные заявки»

### Общие принципы

- В системе настроены **6 ролей**: Администратор, Инициатор (Менеджер), Руководитель подразделения, Казначей, Директор, Бухгалтер.
- Доступ к заявкам разграничен по **стадиям** и по **видимости** (только свои, своего отдела, все).
- Перемещение между стадиями в основном автоматизировано (роботы), но для ряда ролей разрешено ручное перемещение.
- Настройки строго соответствуют регламенту управления платежами и платёжным календарём.

### 1. Администратор
- **Полный доступ** ко всем заявкам на всех стадиях.
- Разрешены: чтение, добавление, изменение, удаление, экспорт, импорт.
- Может перемещать заявки на **любые стадии**.
- Видит **все заявки** без ограничений.

---

### 2. Инициатор (Менеджер)
- **Добавление** – только на стадии *«Черновик»*.
- **Чтение** – только **свои** заявки на стадиях:
  - *«Черновик»*
  - *«На доработке (Инициатор)»*
  - На остальных стадиях чтение закрыто.
- **Изменение** – только **свои** заявки на стадиях *«Черновик»* и *«На доработке»*.
  - Поля *«Сумма»* и *«Получатель»* доступны для редактирования только на этих стадиях.
- **Удаление** – только **свои** заявки на стадии *«Черновик»*.
- **Перемещение** – **запрещено** (все перемещения выполняются роботами или вышестоящими ролями).
- **Видимость** – только свои заявки.

---

### 3. Руководитель подразделения
- **Чтение** – заявки **своего отдела** на стадии:
  - *«Согласование руководителем подразделения»*
  - Также может видеть заявки отдела на *«Черновик»* и *«На доработке»* (для контроля).
- **Добавление** – **не предусмотрено** (создаёт только Инициатор).
- **Изменение** – **запрещено** (только согласование/отклонение).
- **Удаление** – **запрещено**.
- **Перемещение** – может:
  - Утвердить заявку → переместить с *«Согласование руководителем»* на *«Контроль Казначейства»*.
  - Отклонить заявку → переместить на *«На доработке (Инициатор)»* с обязательным комментарием.
- **Видимость** – заявки своего отдела.

---

### 4. Казначей
- **Чтение** – **все заявки** на всех стадиях (включая черновики и доработки).
- **Добавление** – может создавать заявки **прямого списания** (без согласования) – доступно на стадии *«Черновик»*.
- **Изменение** – может редактировать:
  - Поля *«Сумма»* и *«Планируемая дата платежа»* на стадии *«Контроль Казначейства»*.
  - Другие поля при необходимости на тех же стадиях.
- **Удаление** – разрешено (вероятно, на любых стадиях, кроме финальных).
- **Перемещение** – может:
  - Утвердить заявку → переместить с *«Контроль Казначейства»* на *«Утверждение Реестра»*.
  - Вернуть на доработку → переместить на *«На доработке (Инициатор)»*.
  - Инициировать **частичную оплату** (разделение заявки на две).
- **Видимость** – все заявки.

---

### 5. Директор
- **Чтение** – **все заявки** на всех стадиях.
- **Добавление** – **не предусмотрено**.
- **Изменение** – **запрещено** (кроме добавления комментариев).
- **Удаление** – **запрещено**.
- **Перемещение** – может:
  - Утвердить реестр → переместить заявки с *«Утверждение Реестра»* на *«В работе (Бухгалтерия)»*.
  - (Отклонение реестра обычно не практикуется, но технически возможно с комментарием).
- **Видимость** – все заявки.

---

### 6. Бухгалтер
- **Чтение** – **все заявки** на стадиях:
  - *«В работе (Бухгалтерия)»*
  - *«Оплачено»*
  - Также доступны для просмотра другие стадии (для контроля).
- **Добавление** – может создавать заявки **прямого списания** (аналогично Казначею).
- **Изменение** – может корректировать заявки на стадии *«В работе»* (например, реквизиты).
- **Удаление** – **запрещено**.
- **Перемещение** – может:
  - Перевести заявку с *«В работе»* на *«Оплачено»* после фактической оплаты.
  - Перевести на *«Отклонено/Аннулировано»* при необходимости.
- **Видимость** – все заявки (для операционной работы).

---

### Особые настройки (важно!)

| Настройка | Описание |
|-----------|----------|
| **Прямое списание** | Доступно только для ролей **Казначей**, **Бухгалтер** и **Администратор**. При создании такой заявки робот автоматически пропускает стадии согласования и отправляет сразу в *«В работе»*. |
| **Частичная оплата** | Доступна только **Казначею**. Он может разделить заявку на две: одобренную часть и остаток (возвращается на доработку). |
| **Блокировка редактирования** | На стадиях от *«Согласование руководителем»* до *«В работе»* поля *«Сумма»* и *«Получатель»* **заблокированы** для Инициаторов и Руководителей (доступны только Казначею и Бухгалтеру). |
| **Утверждение реестра** | После перехода на стадию *«Утверждение Реестра»* изменение данных **блокируется для всех** (кроме Администратора). |
| **Обязательность комментариев** | При возврате заявки на доработку или отклонении на любой стадии **требуется** текстовый комментарий с причиной. Без него смена статуса технически невозможна. |
| **Тайминги** | Права на перемещение жёстко привязаны к графику платёжного дня (например, утверждение реестра только до 14:30). |

```js
import { Controller, Post, Query, Body, HttpException, HttpStatus } from '@nestjs/common';
import { BitrixSyncService } from './bitrix-sync.service';

@Controller('api/bitrix')
export class BitrixController {
  constructor(private readonly bitrixSyncService: BitrixSyncService) {}

  // ЧИСТЫЙ РОУТ СИНХРОНИЗАЦИИ С ПРИЕМОМ ID ПОЛЬЗОВАТЕЛЯ
  @Post('sync-sap')
  async syncSap(@Query('userId') queryUserId: string, @Body() body: any) {
    try {
      const userId = queryUserId || body?.userId;
      const result = await this.bitrixSyncService.syncContractors(userId);
      return {
        success: true,
        message: 'Синхронизация контрагентов успешно завершена',
        data: result,
      };
    } catch (error) {
      console.error('Ошибка синхронизации:', error);
      throw new HttpException(
        error.message || 'Ошибка во время синхронизации',
        HttpStatus.INTERNAL_SERVER_ERROR,
      );
    }
  }
}

import { Module } from '@nestjs/common';
import { BitrixController } from './bitrix.controller';
import { BitrixSyncService } from './bitrix-sync.service';
import { RawQueryModule } from '../narabotka/raw-query.module';

@Module({
  imports: [RawQueryModule],
  controllers: [BitrixController],
  providers: [BitrixSyncService],
})
export class BitrixModule {}

import { Injectable, OnModuleInit } from '@nestjs/common';
import { RawQueryService } from '../narabotka/raw-query.service';

@Injectable()
export class BitrixSyncService implements OnModuleInit {
  // =========================================================
  // НАСТРОЙКИ СИНХРОНИЗАЦИИ (СПИСКИ)
  // =========================================================
  private readonly B24_WEBHOOK_URL: string = process.env.B24_WEBHOOK_URL || '';
  private readonly IBLOCK_ID: number = Number(process.env.B24_IBLOCK_ID || '30');
  private readonly SAP_CODE_FIELD: string = process.env.B24_SAP_CODE_FIELD || '';
  private readonly IBLOCK_TYPE_ID: string = process.env.B24_IBLOCK_TYPE_ID || '';
  // =========================================================

  constructor(private readonly rawQueryService: RawQueryService) {}

  // Автозапуск планировщика при старте сервера
  async onModuleInit() {
    const timerEnabled = process.env.B24_SYNC_TIMER_ENABLED !== 'false';

    if (!timerEnabled) {
      console.log('⏸ Таймер автосинхронизации SAP выключен через B24_SYNC_TIMER_ENABLED=false');
      return;
    }

    const intervalMinutes = Number(process.env.B24_SYNC_INTERVAL_MINUTES || 1440);

    const safeIntervalMinutes =
      Number.isFinite(intervalMinutes) && intervalMinutes > 0
        ? intervalMinutes
        : 1440;

    const intervalMs = safeIntervalMinutes * 60 * 1000;

    console.log(
      `⏳ Таймер автосинхронизации SAP запущен: каждые ${safeIntervalMinutes} минут.`,
    );

    setInterval(async () => {
      try {
        const adminUserId = process.env.B24_ADMIN_USER_ID || '196';

        console.log('⏰ Запуск автоматической синхронизации SAP по таймеру...');

        await this.syncContractors(adminUserId, 'auto');
      } catch (err) {
        console.error('❌ Ошибка автоматической синхронизации по таймеру:', err);
      }
    }, intervalMs);
  }

  async syncContractors(
    userId?: string,
    source: 'manual' | 'auto' = 'manual',
  ): Promise<{ added: number; updated: number; totalInDb: number }> {
    const dbResult =
      await this.rawQueryService.executeStoredProcedure(
        'dbo.GetContractorsForB24Sync',
      );

    const sqlContractors = dbResult.data || [];

    if (sqlContractors.length === 0) {
      return { added: 0, updated: 0, totalInDb: 0 };
    }

    const b24Elements = await this.getAllB24ListElements();

    const b24Map = new Map<string, { id: number; title: string }>();

    for (const element of b24Elements) {
      const propObj = element[this.SAP_CODE_FIELD];
      let code = '';

      if (propObj) {
        const values = Object.values(propObj);

        if (
          values.length > 0 &&
          values[0] !== null &&
          values[0] !== undefined
        ) {
          code = String(values[0]).trim();
        }
      }

      if (code) {
        b24Map.set(code, {
          id: parseInt(element.ID, 10),
          title: element.NAME,
        });
      }
    }

    const toCreate: { title: string; cardCode: string }[] = [];
    const toUpdate: { id: number; title: string }[] = [];

    for (const contractor of sqlContractors) {
      const cardCode = contractor.CardCode
        ? contractor.CardCode.toString().trim()
        : '';

      const cardName = contractor.CardName
        ? contractor.CardName.toString().trim()
        : '';

      if (!cardCode || !cardName) continue;

      const existing = b24Map.get(cardCode);
      const expectedTitle = `${cardName} (${cardCode})`;

      if (!existing) {
        toCreate.push({ title: expectedTitle, cardCode });
      } else if (existing.title !== expectedTitle) {
        toUpdate.push({ id: existing.id, title: expectedTitle });
      }
    }

    if (toCreate.length > 0) {
      await this.executeBatchCreate(toCreate);
    }

    if (toUpdate.length > 0) {
      await this.executeBatchUpdate(toUpdate);
    }

    // Если передан ID пользователя — отправляем ему уведомление в Битрикс24
    if (userId) {
      await this.sendB24Notification(
        userId,
        toCreate.length,
        toUpdate.length,
        source,
      );
    }

    return {
      added: toCreate.length,
      updated: toUpdate.length,
      totalInDb: sqlContractors.length,
    };
  }

  // Получение элементов Списка из Битрикса с пагинацией (по 50 штук)
  private async getAllB24ListElements(): Promise<any[]> {
    const elements: any[] = [];
    let start = 0;
    let hasMore = true;

    while (hasMore) {
      const url = `${this.B24_WEBHOOK_URL}lists.element.get`;

      const response = await fetch(url, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({
          IBLOCK_TYPE_ID: this.IBLOCK_TYPE_ID,
          IBLOCK_ID: this.IBLOCK_ID,
          start: start,
        }),
      });

      const result = await response.json();

      if (result.result) {
        elements.push(...result.result);
      }

      if (result.next) {
        start = result.next;
      } else {
        hasMore = false;
      }
    }

    return elements;
  }

  // Быстрое пакетное создание элементов в Списке (по 50 за 1 запрос)
  private async executeBatchCreate(
    items: { title: string; cardCode: string }[],
  ): Promise<any> {
    const batchSize = 50;

    for (let i = 0; i < items.length; i += batchSize) {
      const chunk = items.slice(i, i + batchSize);

      const cmd: Record<string, string> = {};

      chunk.forEach((item, index) => {
        const titleEsc = encodeURIComponent(item.title);
        const codeEsc = encodeURIComponent(item.cardCode);

        cmd[`cmd_${index}`] =
          `lists.element.add?` +
          `IBLOCK_TYPE_ID=${this.IBLOCK_TYPE_ID}` +
          `&IBLOCK_ID=${this.IBLOCK_ID}` +
          `&ELEMENT_CODE=${codeEsc}` +
          `&FIELDS[NAME]=${titleEsc}` +
          `&FIELDS[${this.SAP_CODE_FIELD}]=${codeEsc}`;
      });

      const url = `${this.B24_WEBHOOK_URL}batch`;

      const response = await fetch(url, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ halt: 0, cmd }),
      });

      await response.json();
    }
  }

  // Быстрое пакетное обновление элементов в Списке (по 50 за 1 запрос)
  private async executeBatchUpdate(
    items: { id: number; title: string }[],
  ): Promise<any> {
    const batchSize = 50;

    for (let i = 0; i < items.length; i += batchSize) {
      const chunk = items.slice(i, i + batchSize);

      const cmd: Record<string, string> = {};

      chunk.forEach((item, index) => {
        const titleEsc = encodeURIComponent(item.title);

        cmd[`cmd_${index}`] =
          `lists.element.update?` +
          `IBLOCK_TYPE_ID=${this.IBLOCK_TYPE_ID}` +
          `&IBLOCK_ID=${this.IBLOCK_ID}` +
          `&ELEMENT_ID=${item.id}` +
          `&FIELDS[NAME]=${titleEsc}`;
      });

      const url = `${this.B24_WEBHOOK_URL}batch`;

      const response = await fetch(url, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ halt: 0, cmd }),
      });

      await response.json();
    }
  }

  // Метод отправки системного уведомления в колокольчик Битрикс24
  private async sendB24Notification(
    userId: string,
    added: number,
    updated: number,
    source: 'manual' | 'auto' = 'manual',
  ): Promise<void> {
    try {
      // Очищаем ID пользователя (Битрикс иногда передает его как "user_196", превращаем в "196")
      const cleanUserId = userId.replace('user_', '');

      const url = `${this.B24_WEBHOOK_URL}im.notify.system.add`;

      const title =
        source === 'auto'
          ? '⏰ [b]Автоматическое обновление SAP по таймеру завершено![/b]'
          : '🔄 [b]Синхронизация SAP успешно завершена![/b]';

      const message =
        `${title}\n` +
        `• Добавлено новых контрагентов: [b]${added}[/b]\n` +
        `• Обновлено названий: [b]${updated}[/b]`;

      await fetch(url, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({
          USER_ID: cleanUserId,
          MESSAGE: message,
          // Ссылка, которая откроется при клике на уведомление (ведет прямо в ваш Список №30)
          URL: `https://grosver-group.bitrix24.by/company/lists/${this.IBLOCK_ID}/`,
        }),
      });
    } catch (error) {
      console.error('Ошибка отправки уведомления в Битрикс24:', error);
    }
  }
}
```

## Бизнес процессы

### Обновить контрагентов из SAP

Пользовательское название:	
- Исходящий Вебхук
- https://meridian-sap-api.shares.zrok.io/api/bitrix/sync-sap?userId={{Кем создан}}

### Общее

Для того чтобы выгрузить всю конфигурацию смарт-процесса (структуру, поля, карточку, стадии, БП и роботов), вам нужно сделать серию POST-запросов к вашему вебхуку.

Для примеров ниже мы предполагаем, что **ID вашего смарт-процесса (entityTypeId)** равен `128` (обычно смарт-процессы начинаются со 128, 130 и т.д.). Подставьте свой ID вместо 128.

Базовый URL для всех запросов:
`POST https://grosver-group.bitrix24.by/rest/<user_id>/<webhook_key>/<МЕТОД>`

---

### 1. Настройки самого смарт-процесса
Выгружает основные настройки: включены ли воронки, стадии, роботы, корзина, печать документов и прочее.
*   **Метод:** `crm.type.getByEntityTypeId` (если вы знаете именно `entityTypeId`, например 128) или `crm.type.get` (если вы знаете порядковый ID типа, например 1)
*   **Тело запроса (JSON):**
```json
{
  "entityTypeId": 128
}
```

### 2. Все поля смарт-процесса
Выгружает список и настройки всех системных и пользовательских полей, которые есть в этом смарт-процессе.
*   **Метод:** `crm.item.fields`
*   **Тело запроса (JSON):**
```json
{
  "entityTypeId": 128
}
```

### 3. Внешний вид (настройки) карточки
Позволяет получить конфигурацию того, как поля расположены по секциям (разделам) внутри самой карточки CRM.
*   **Метод:** `crm.item.details.configuration.get`
*   **Тело запроса (JSON):**
```json
{
  "entityTypeId": 128
}
```
*(Примечание: Если у вас несколько воронок и для каждой своя карточка, нужно добавить параметр `extras: {"categoryId": <ID_воронки>}`)*

### 4. Воронки (Направления)
Если в смарт-процессе включены воронки, этот метод выгрузит их список.
*   **Метод:** `crm.category.list`
*   **Тело запроса (JSON):**
```json
{
  "entityTypeId": 128
}
```

### 5. Стадии (Этапы)
Выгружает канбан-стадии смарт-процесса.
*   **Метод:** `crm.status.list`
*   **Тело запроса (JSON):**
```json
{
  "filter": {
    "ENTITY_ID": "DYNAMIC_128_STAGE_0"
  }
}
```
*(Важно: Если смарт-процесс использует воронки, вместо `0` на конце нужно указать ID воронки из предыдущего запроса. Например, `DYNAMIC_128_STAGE_14`)*

### 6. Бизнес-процессы и Роботы
Бизнес-процессы и роботы в Битрикс24 — это, технически, одни и те же шаблоны (у роботов есть системные флаги или настройки автоматического запуска при смене стадии). Этот запрос выгрузит их все, включая их «внутрянку» — схему блоков, переменные и константы.
